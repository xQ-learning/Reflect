# 漏洞报告审阅系统 · 需求文档

> **文档性质**：可移交下一会话的完整需求说明书。
> **基线来源**：本仓库 `Reflect 复盘`（v2.10.0，分支 `feat/aurora-theme`，提交 `d0a6c36`）——本项目复用其技术栈、架构与视觉风格。
> **状态**：需求已确认，尚未开工。
> **下一步**：按 §10 的实施顺序，从 §4 的数据模型开始。

---

## 1. 项目目标

开发一个**漏洞报告审阅系统**（暂定代号 `SecReview`），用于本地撰写、导入、归档漏洞报告。

**核心诉求**：
- 报告是核心页，可撰写、可导入报告内容、可导入报告模板
- 横向三个板块：**漏洞 / 报告 / 统计**
- 整体架构与视觉风格沿用 Reflect v2.10.0

**明确不做**（已确认）：
- ❌ 不做「提交审阅 → 通过 / 驳回」的流转状态机。只要**撰写**与**归档**两个动作。
- ❌ 不上架任何应用商店（iOS 侧仅需可安装可运行）。
- ❌ 不做后端、不做多设备同步、不做账号体系。数据全部存本机。

## 2. 与 Reflect 的对应关系

这是本项目最重要的设计约束：**新系统的每一层都能在 Reflect 里找到对应物**。复用时按下表对照。

| Reflect（基线） | 本项目 | 复用方式 |

| `统计` 板块 | **`统计`** 板块 | 同上 |

| 复盘（Review）工作台 | 报告（Report）撰写页 | 交互流程照抄 |
| 验证标准（criteria） | 报告模板的章节清单 | 结构同构 |
| 事实（facts）+ 情绪标签 | 报告的正文段落 | — |
| 原因 / 改进措施 | 归档备注 / 复现步骤 | — |
| 战报回放（只读页） | 报告预览（只读页） | 结构照抄 |

**结论**：Web 层 3002 行 JS + 1274 行 CSS 中，**只有 `store.js` 的数据模型和 `ui.js` 的渲染逻辑需要重写**，`compare.js` / `export.js` 是改写而非重写，CSS 完全沿用。

## 3. 技术栈（完全沿用基线）

| 层 | 技术 | 版本 / 约束 |
|---|---|---|
| 形态 | 原生 Android 应用（APK），纯本地离线 | 无后端、无网络请求 |

| 数据 | `localStorage` 单 key 存全量 JSON | 带损坏备份 key |
| 路由 | Hash 路由 | `#/vulns` / `#/reports` / `#/stats` |
| 图标 | 内联 SVG / emoji | 零外部资源 |
| 构建 | 纯 SDK 工具链，**无 Gradle / Node / npm / pip** | `aapt2` → `javac` → `d8` → `zipalign` → `apksigner` |
| 签名 | 自签 keystore（首次自动生成） | 永久有效，同密钥可覆盖安装 |

**沿用基线的约束（务必保持）**：
- 不引入任何第三方依赖，不引入 npm / pip / Gradle
- JS 一律经典 `<script>` 顺序加载（`file://` 下 ES module 不可用）
- 图标全部内联 SVG / emoji，不引外部字体或图片
- 构建脚本保持单文件 shell 脚本，可读性优先

## 4. 数据模型

### 4.1 顶层结构

```js
state = {
  vulns: [Vulnerability],
  reports: [Report]
}
```

**漏洞与报告的关系**：与 Reflect 中「目标 ↔ 复盘」的**实现层面关联**一致 —— 两者是**并列的两级实体**，漏洞是待审阅的对象，报告是针对漏洞产出的交付文档。

- 一个漏洞**可以产出多份报告**（如同一个目标可以有多轮复盘记录）
- 一份报告**必须挂在某个漏洞下**（`report.vulnId` 指向 `vuln.id`）
- 报告可独立于漏洞存在状态（草稿 / 已归档）

> ⚠️ **待下一会话确认**：若实际需求是「漏洞与报告严格 1:1」，只需把 `reports` 数组改为嵌套在 `vuln.reports` 里，其余设计不受影响。

### 4.2 Vulnerability（漏洞）

```js
{
  id: 'v-xxxx',              // uid('v')
  title: '',                 // 漏洞标题（必填）
  severity: 'high',          // 严重级别：critical / high / medium / low / info
  target: '',                // 受影响组件 / 目标系统
  description: '',           // 漏洞描述（摘要）
  cve: '',                   // CVE / 编号（可选）
  reporter: '',              // 报告来源方（可选）
  discoveredAt: '',          // 发现日期（字符串，可选）
  createdAt: 0,              // 时间戳
  updatedAt: 0
}
```

**严重级别枚举**（沿用基线的状态色体系）：

| 值 | 中文 | 颜色 | 对应基线变量 |
|---|---|---|---|
| `critical` | 严重 | 暗红 | `--danger` |
| `high` | 高危 | 琥珀偏红 | 新增 `--sev-high` |
| `medium` | 中危 | 琥珀 | `--warn` |
| `low` | 低危 | 香槟金 | `--gold` |
| `info` | 信息 | 银灰 | `--muted` |

### 4.3 Report（报告）

```js
{
  id: 'r-xxxx',              // uid('r')
  vulnId: 'v-xxxx',          // 关联漏洞
  title: '',                 // 报告标题
  templateId: 'generic',     // 使用的模板 id
  content: '',               // 正文（纯文本 / 轻 Markdown）
  status: 'draft',           // draft（撰写中）/ archived（已归档）
  notes: '',                 // 归档备注
  createdAt: 0,
  updatedAt: 0,
  archivedAt: 0              // 归档时间，0 = 未归档
}
```

**状态只有两个**（已确认不做审阅流转）：
- `draft` —— 撰写中
- `archived` —— 已归档

### 4.4 报告模板（内置模板库）

模板**内置在代码里**（用户已确认「内置模板库」方案），不来自文件导入。

模板数据结构：

```js
{
  id: 'generic',
  name: '通用漏洞报告',
  desc: '适用于大多数漏洞的标准结构',
  sections: [
    { key: 'summary',  label: '漏洞概述', hint: '一两句话说清是什么漏洞' },
    { key: 'detail',   label: '漏洞描述', hint: '原理、触发条件、代码位置' },
    { key: 'impact',   label: '影响范围', hint: '受影响的资产与业务后果' },
    { key: 'repro',    label: '复现步骤', hint: '可照着做一遍的步骤' },
    { key: 'evidence', label: '证据',     hint: '截图、请求响应、日志' },
    { key: 'fix',      label: '修复建议', hint: '怎么改，改哪里' },
    { key: 'ref',      label: '参考资料', hint: 'CVE 链接、厂商公告' }
  ]
}
```

**内置模板清单**（起步 4 个，按需增补）：

| id | 名称 | 适用 |
|---|---|---|
| `generic` | 通用漏洞报告 | 绝大多数情况 |
| `web` | Web 应用漏洞报告 | 侧重输入点、请求构造、响应 |
| `logic` | 逻辑漏洞报告 | 侧重业务流、越权路径、权限矩阵 |
| `supply` | 组件/供应链漏洞报告 | 侧重组件版本、CVE、依赖路径 |

**模板的两种用法**：
1. **新建报告时选模板** → 生成带章节骨架的报告，各章节按 `hint` 提示撰写
2. **已有报告时切换模板** → 保留已有正文，追加缺失章节

### 4.5 导入报告内容（从本地文件）

用户已确认：**从本地文件导入**。

- 通过原生桥新增 `pickFile` 方法，弹系统文件选择器
- 支持格式：`.md` / `.txt` / `.markdown`
- 导入后填入 `report.content`，并尝试**按 Markdown 标题（`#`）自动切分章节**，回填到模板各 section
- 导入是**覆盖式**（进弹层让用户确认），不静默覆盖已有正文

> ⚠️ **原生桥需新增方法**：基线的 `AndroidBridge` 只有 `saveFile` / `share` / `toast` 三个方法。
> 新增 `pickFile` 需要在 `MainActivity.java` 里加 `startActivityForResult` / `ActivityResultLauncher` 逻辑，
> 读文件后回调 JS。这是**唯一需要改原生壳的地方**。
> iOS 侧对应 `UIDocumentPickerViewController`。

### 5.3 漏洞索引页（`#/vulns`）

照抄基线 `renderGoals()`（`ui.js:343`）的结构：

- 卡片列表：每张卡显示**严重级别徽章 + 标题 + 受影响组件 + 关联报告数 + 更新时间**
- 按更新时间倒序
- 空态：`.empty` 组件 + 「新建漏洞」主按钮
- 顶栏右侧：新建漏洞的图标按钮
- **长按卡片弹删除菜单**（基线 `startPress()` 逻辑，`ui.js:1167` 起，照搬）

### 5.4 漏洞详情页（`#/vulns/:id`）

对应基线的「战报回放」只读页（`renderBattle()`，`ui.js:843`）：

- 顶栏居中标题「漏洞详情」，左右是无边框纯文字（基线 `.appbar.center` 样式）
- 主体：漏洞字段逐项展示（`cmp` 网格样式）
- 下半部分：关联报告列表（可点进报告撰写页）
- 无底栏（用基线 `body.no-tabs` 铺满到底）

### 5.5 报告撰写页（`#/reports/:id`）★ 核心页

照抄基线 `renderReview()`（`ui.js:699`）的结构 —— **顶部悬浮步骤条 + 纵向三块**。

**顶部步骤条**（基线 `.bstrip`，`ui.js:403` 的 `STEP_ITEMS`）：

| 步骤 | 图标 | 内容 |
|---|---|---|
| 1 | 📝 | 报告信息（标题、关联漏洞） |
| 2 | 📄 | 报告正文（按模板章节） |
| 3 | 📦 | 归档与导出 |

**块 1 · 报告信息**
- 报告标题（必填）
- 关联漏洞（下拉选择，可跳转到漏洞详情）
- 填好后自动折叠成摘要，点一下展开改（基线 `expandGoal` / `expandResult` 机制）

**块 2 · 报告正文**（核心）
- 顶部两个动作按钮：
  - 「导入报告内容」→ 调原生 `pickFile`，选文件后进确认弹层，展示预览，确认后写入
  - 「套用模板」→ 弹层列出内置模板，选中后套用章节骨架
- 正文区：按当前模板的 sections 逐节渲染，每节一个 `.field` + `textarea`，带 `hint` 占位提示
- 若报告尚无模板，默认套用 `generic`

**块 3 · 归档与导出**
- 「归档」按钮：把 `status` 从 `draft` 改为 `archived`，记录 `archivedAt`
- 「导出报告」：调基线 `openExportModal()`（`ui.js:1103`）弹层，展示 Markdown 预览，提供「复制 / 分享 / 写入文件」三个动作
- 已归档的报告：块 3 显示「取消归档」

**底部主按钮**：`提交归档` / `取消归档`（基线 `submit-review` 的位置）

### 5.6 报告索引页（`#/reports`）

- 卡片列表：报告标题 + 关联漏洞标题 + 状态徽章（撰写中 / 已归档）+ 更新时间
- 顶部一行筛选：全部 / 撰写中 / 已归档
- 点卡片进报告撰写页

### 5.7 统计页（`#/stats`）

照抄基线 `renderStats()`（`ui.js:912`）：

**概览区**（`.stat-grid` 四宫格）
- 漏洞总数
- 报告总数
- 已归档报告数
- 平均严重度得分（critical=5 … info=1 的均值）

**按严重级别分布**（`.progress` 进度条样式，基线 `progress > i` 已带金属渐变）

**疑似重复漏洞**（复用 `compare.js` 的 `similarity()` 算法，`compare.js:161`）
- 两两比对漏洞的 `title + description`
- 相似度 ≥ 0.45 的列为「疑似重复」
- 基线 `repeatedCauses()` 的四路信号混合算法**直接复用**，只换比对字段

**导出全部报告**按钮（基线 `export-all`）

## 7. 视觉规范（沿用，不重新设计）

**唯一视觉基线**：`Reflect` v2.10.0「暗金金属」主题。完整规范见基线仓库 `README.md` 的「UI 视觉规范：暗金金属」一节（`style.css:1061-1274` 是其实现）。

**三条核心手法**（新组件必须遵守）：

| 招 | 做法 |
|---|---|
| 金属倒角高光 | 顶边 `--bevel` 亮一档、底边压暗、内侧顶光晕，替代纯色线框 |
| 暗金渐变与弥散阴影 | `--metal-face` 受光面 + 弥散影 + 按下 `scale(.985)`，替代平涂色块 |
| 微光呼吸感 | 选中态辉光 2.8s 起伏，`prefers-reduced-motion` 时关闭 |

**硬性规则**：
- 文字不用纯白：标题 `#F3F4F6`、正文 `#9CA3AF`、提示 `#868B95`、图标 `#4B5563`
- 香槟金只做小面积点缀，不大面积铺底
- 一切可点元素最小高度 44px（`--tap`）
- 新组件的金属质感加在 `style.css` 末尾「金属质感层」那一段，不要散落到前面
